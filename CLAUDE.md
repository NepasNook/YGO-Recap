# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

**YGO Recap** — a Yu-Gi-Oh! duel / tournament tracker (leaderboard, live duel room with LP calculator, decks, tournaments, admin panel). Scaffolded from a Lovable TanStack Start template and currently hosted there; the build targets Cloudflare Workers. Supabase is the entire backend.

UI copy is mixed: leaderboard/tournaments are mostly English, the duel flow is Italian. Match the language of the surrounding screen when adding strings.

## Commands

```bash
npm run dev        # vite dev — port 3000 (see .claude/launch.json)
npm run build      # vite build (Cloudflare Workers output)
npm run build:dev  # build with development mode
npm run preview
npm run lint       # eslint (prettier runs as an eslint rule — lint fails on formatting)
npm run format     # prettier --write .
```

There is no test suite and no typecheck script; `tsc --noEmit -p tsconfig.json` is the way to type-check.

## Architecture

### Framework wiring (easy to break)

- `vite.config.ts` wraps `@lovable.dev/vite-tanstack-config`, which **already** registers tanstackStart, React, Tailwind, tsconfig paths, the Cloudflare plugin, and `VITE_*` env injection. Adding any of those plugins manually duplicates them and breaks the build. Extra config goes through `defineConfig({ vite: { ... } })`.
- `src/server.ts` is the Worker entry (`wrangler.jsonc` → `main`, plus `tanstackStart.server.entry` in `vite.config.ts` — both are needed). It wraps the TanStack server entry to render a branded 500 page, including for errors h3 swallows into a `{"unhandled":true,"message":"HTTPError"}` JSON 500.
- `src/start.ts` registers the global middleware: `attachSupabaseAuth` (client-side, puts the bearer token on every serverFn RPC) and an SSR error middleware. Removing `attachSupabaseAuth` silently unauthenticates all server functions.
- `src/routeTree.gen.ts` is generated by the router plugin — never edit it by hand.

### Routing & auth

File-based routes in `src/routes`. `_authenticated.tsx` is a **client-side** guard only (redirects to `/login` once `useAuth()` resolves) — it is not a security boundary. All real authorization lives in Postgres RLS policies.

`src/components/AuthProvider.tsx` is the single auth source: session via `supabase.auth`, plus `profile` and `isAdmin` (derived from the `user_roles` table). `isAdmin` gates the Admin nav item and the `/admin` page client-side; the DB enforces it via `has_role()`.

### Data access

All data access is **direct client-side Supabase calls guarded by RLS** — there are currently no `createServerFn` server functions, and `supabaseAdmin` / `requireSupabaseAuth` exist but are unused. Prefer keeping that pattern (write an RLS policy or a `SECURITY DEFINER` RPC) rather than introducing a service-role path.

Files under `src/integrations/supabase/` are marked _"automatically generated"_ (`client.ts`, `client.server.ts`, `auth-middleware.ts`, `auth-attacher.ts`, `types.ts`). `types.ts` mirrors the Supabase schema — regenerate/update it after every migration, otherwise inserts need even more `as never` casts (existing code uses `.insert({...} as never)` where the generated types are too strict).

### Live duel room (`src/routes/_authenticated/duel.$id.tsx`)

The most intricate part of the app:

- `duels` holds the match record; `duel_live_state` (1:1 with `duels`) holds the shared mutable state — LP, game wins, draws, `starter`, and `last_event` (jsonb).
- One Supabase Realtime channel per duel subscribes to UPDATEs on `duels` and `duel_live_state` and INSERTs on `duel_lp_logs`.
- Dice / coin / start-of-duel rolls are **not** local UI state: the roller writes `last_event = {type, value, at: Date.now()}` and both clients open the same dialog. Deduping is by the `at` timestamp (`lastEventAtRef`) — keep writing a fresh `at` or the popup won't re-fire.
- Only the host (player1) triggers the start-of-duel dice roll, so it happens exactly once.
- Join flow: host creates a duel with `status: 'waiting_opponent'` → joiner sets `pending_join_user_id` → host accepts, setting `player2_id` + `status: 'live'`. A 2s polling loop backs up Realtime while waiting for a join, so dropped messages don't strand the host.
- Every LP change is appended to `duel_lp_logs` (with `prev_lp`/`new_lp`/`delta`); rows with a `note` are narrative events (e.g. the starting dice roll) rather than LP deltas. Undo deletes the newest non-note log and restores `prev_lp`.
- Match is best-of-3: `declareWinner` inserts a `duel_games` row, bumps `games_pX_wins`, and at 2 wins sets `duels.winner_id` + `status: 'finished'` (and back-fills `tournament_matches.winner_id` when the duel was launched from a tournament match via `?match=<id>`).
- Duels flagged `for_fun` or `is_local` are recorded but `for_fun` ones are excluded from Elo.

### Stats & tournaments

- Win-rate leaderboard reads the `user_stats` view; the Elo leaderboard calls the `compute_elo_ratings()` RPC, which recomputes ratings on the fly on every call (K=32, base 1500, `for_fun` excluded, only duels from the `2026-07-17` cutoff onward, every profile returned even with 0 duels). A previous trigger-based "live Elo" column was deliberately reverted — see `supabase/migrations/20260717151855_elo_from_cutoff_date.sql`.
- Tournament pairings are generated **client-side** by `src/lib/tournamentBracket.ts` (single-elimination bracket padded to a power of two, or round-robin via the circle method with a BYE for odd counts) and bulk-inserted into `tournament_matches`. Tournament matches spawn regular duels that link back through `tournament_matches.duel_id`.

### Database & migrations

`supabase/migrations/*.sql`, timestamp-prefixed and applied in order. Conventions that migrations must keep:

- RLS enabled on every table; policies use `public.has_role(auth.uid(), 'admin')` — a `SECURITY DEFINER STABLE` function with `SET search_path = public`, which exists specifically to avoid recursive RLS on `user_roles`. Roles live in `user_roles`, never on `profiles`.
- Tables read via Realtime need both `ALTER PUBLICATION supabase_realtime ADD TABLE ...` and `REPLICA IDENTITY FULL`; later migrations guard those with `pg_publication_tables` lookups so re-runs are idempotent.
- `public_profiles` is the anon-safe view of `profiles`; `admin_list_user_emails()` is the only path to auth emails and is `SECURITY DEFINER` + `has_role`-gated.
- Admin bootstrap: `grant_bootstrap_admin()` (trigger on `auth.users`) grants `admin` to anyone signing up with an address listed in `private.admin_bootstrap_emails`. That table lives in the unexposed `private` schema and is seeded **manually** from the Supabase SQL editor — never hardcode an email in a migration.

### Styling

Tailwind v4, CSS-first: all tokens live in `src/styles.css` under `@theme inline` / `:root`. Dark navy + gold theme only — there is no light mode. Reuse the custom utilities (`gold-text`, `gold-gradient`, `card-mystic`, `glow-gold`, `text-gold`) and the `font-display` (Cinzel) family instead of hardcoding colors. shadcn/ui ("new-york", lucide icons) components live in `src/components/ui`; `@/*` maps to `src/*`.

## Notes

- `.env` is gitignored; `.env.example` is the versioned template. It holds the Supabase URL + publishable (anon) key under both `VITE_*` (client) and bare (SSR) names. `SUPABASE_SERVICE_ROLE_KEY` is intentionally absent — it must never land there; use the deploy platform's secrets instead.
- Prettier: 100 cols, double quotes, trailing commas. `@typescript-eslint/no-unused-vars` is off; importing `server-only` is a hard error (use `*.server.ts` naming instead).
